# 広聴AIをイベント時だけ起動する方式の比較

Issue #25 の調査結果である。ADR-0001 で「広聴AIはイベント時だけ起動する」と決めた。本アプリはサーバレスなので、広聴AIを起動・停止する方式が未決だった。

確認日は2026-10-25である。「計測」は実際に測った値、「推定」は根拠から見積もった値、「未確認」は調べきれていない値を指す。

## 結論

**Fargateで、イベント時だけタスクを起動する方式を推奨する。**
CIで作った広聴AIのイメージをECRに置き、分析の直前にタスクを起動し、結果を取り込んだら止める。

- 待ち時間は、冷えた状態で約3〜4分、準備済みなら約2分である（40件の場合。推定を含む）
- 運営者の画面に「分析を準備する」を置き、セッションの開始前に起動しておく
- 費用は、4時間のイベントで0.2ドル程度である（米国東部の単価での概算。東京は未確認）
- Lambdaのコンテナ（CLIを同期実行）は、有力な代替案である。試作で比べる（後述）

## 計測した値

広聴AIのapiイメージを、固定したコミットでビルドして起動した。
GitHub Actionsの標準ランナーで、キャッシュなしの状態である。

| 項目 | 値 | 区分 |
| --- | --- | --- |
| イメージのビルド時間 | 33秒 | 計測 |
| イメージのサイズ | 1,876MB（展開後） | 計測 |
| 起動から応答まで | 4.1秒 | 計測 |
| 起動直後のメモリ | 130MiB | 計測 |
| 40件の分析 | 約125秒 | 計測（#3の評価） |
| 分析中のメモリの最大 | — | 未確認 |
| 件数を増やしたときの時間 | — | 未確認 |

- 構成はPython 3.12、CPU版のtorchである。`analysis-core[full]` を入れる
- 同梱のDockerfileの起動コマンドは `--reload` 付きで、開発用である。本番用に上書きする
- 結果はコンテナ内のファイル（`LocalStorageService`）に保存される。コンテナを止めると消える。本アプリは完了直後に結果を取り込むので、取り込む前に止めない

## 候補の比較

| 項目 | A. Fargateの都度起動 | B. Lambdaのコンテナ | C. GitHub Actions | D. 常時起動 |
| --- | --- | --- | --- | --- |
| 起動の待ち | 約1〜2分（推定） | 初回は数十秒（未確認） | 約2分以上（#3で計測） | なし |
| 実行時間の上限 | 実質なし | 15分 | 長い（上限は別に確認） | なし |
| 費用の傾向 | 使った秒数だけ | 使った秒数だけ | 無料枠内ならほぼなし | 常に発生 |
| 広聴AIの呼び方 | HTTP API（今の実装） | CLIの同期実行（別の実装） | CLI | HTTP API |
| 参加者の意見の扱い | AWS内で完結 | AWS内で完結 | リポジトリのワークフローを経由 | AWS内で完結 |
| 運用の手間 | イメージとタスク定義 | イメージと関数 | ワークフローと権限 | 常時の監視 |

### A. Fargateの都度起動

- 料金は、vCPU時間とメモリ時間で、秒単位に課金される。最低1分である
- 米国東部のLinux/x86の単価は、1 vCPUあたり0.04048ドル/時、1 GBあたり0.004445ドル/時である
- 1 vCPU・2GBなら、約0.049ドル/時になる。4時間のイベントで約0.2ドルである
- 東京の単価は、確認できなかった。米国東部より高いと思われる。実装前に料金計算ツールで確認する
- 待ちの内訳は、タスクの確保、イメージの取得、起動4秒である。イメージの取得は未計測で、1〜2分と推定する

### B. Lambdaのコンテナ

- コンテナイメージは10GBまで、実行時間は900秒（15分）までである
- 1,876MBのイメージは、サイズの上限に収まる
- 広聴AIのAPIは、202を返したあとに、バックグラウンドで分析を続ける。Lambdaは応答のあとに実行が止まるので、そのままでは合わない（推定）
- このため、CLI（`kouchou-analyze`）を同期実行する形になる。広聴AIの内部の既定プロンプトを使えるので、プロンプトを設定で渡す必要がなくなる
- 15分に収まる件数の上限は、未確認である

### C. GitHub Actions

- 評価（#3）では、この方式で動かせた。パッケージのインストールに約2分かかった
- 参加者の意見を、リポジトリのワークフローに渡すことになる。入力の受け渡し、ログ、成果物の扱いに注意が要る
- 本アプリから起動するために、リポジトリを操作できる資格情報を持つ必要がある
- 評価用としては有用だが、本番の分析には使わない

### D. 常時起動

- 1 vCPU・2GBを1か月つけると、約36ドルになる（米国東部の単価で概算）
- ADR-0001 で、イベント時だけ起動すると決めたので、採用しない

## 推奨案の理由

- 今の実装（HTTP APIのアダプター）を、そのまま使える
- 実行時間に上限がなく、件数が増えても使える
- イメージが約1.9GBで起動が4秒なので、待ちの大半はタスクの確保とイメージの取得である。事前の「準備」で隠せる
- 参加者の意見が、AWSの外に出ない

## 待ち時間の見積り

40件の場合の見積りである。

| 場面 | 起動 | 分析 | 合計 |
| --- | --- | --- | --- |
| 準備なし | 約1〜2分（推定） | 約2分（計測） | 約3〜4分 |
| 準備済み | なし | 約2分（計測） | 約2分 |

件数が増えると、分析の時間は延びる。何件まで許容できるかは、計測が要る。

## 依存の固定

- CIで、広聴AIの固定したコミットからイメージを作り、ECRに置く
- `polars<2` の制約を、イメージのビルドに含める（#3で必要だった）
- コミットの更新は、手動で行い、評価（`eval/kouchou/`）を通してから採用する
- 起動コマンドは `--reload` を外して上書きする
- 管理用のAPIキー（`ADMIN_API_KEY`）は、起動のたびに乱数で作り、タスクと本アプリだけが知る

## 未確認の点と次の作業

- Lambdaのコンテナ（CLIの同期実行）を試作して、Fargateと比べる
