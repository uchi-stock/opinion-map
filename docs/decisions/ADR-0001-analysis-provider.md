# ADR-0001: 分析基盤に広聴AIを別プロセスのHTTP APIとして使う

- Status: Proposed
- Date: 2026-10-25

## Context

意見のクラスタリングを行う分析基盤が必要である。
候補は広聴AI、Polis、いどばた、独自実装である。

調査と評価の結果を次に示す。

- [分析基盤候補OSSのライセンスと保守状況](../oss-candidates-license.md)
- [広聴AIの評価結果（Issue #3）](https://github.com/uchi-stock/opinion-map/issues/3#issuecomment-6397060840)

評価で分かった点は次のとおりである。

- 広聴AIはAGPL-3.0である。HTTP API（FastAPI）があり、`POST /admin/reports` で非同期に分析できる
- サンプル40件を約125秒で分析できた。使用トークンは約4.1万である
- クラスタは概ね妥当で、各意見から元の投稿へ戻れる
- 40件のうち4件が結果から脱落した。元にない文が1件生成された
- 意見どうしの相違点・議論の問い・結果の編集は、広聴AIにない

## Decision

広聴AIを、別プロセスのHTTP APIとして使う。
コードの組み込みとフォークは行わない。

アプリの構成は次のとおりとする。

- イベント・投稿・分析履歴・議論結果は、本アプリのDBを正本とする
- 分析基盤は `AnalysisProvider` アダプター越しに接続し、結果を独自の型に正規化する
- 分析はジョブとして非同期に実行し、入力のスナップショットを保存する

広聴AIにない機能は、本アプリ側で作る。

| 不足 | 本アプリでの対応 |
| --- | --- |
| 脱落した意見 | 入力IDのうち結果にないものを「未分類」として必ず表示する |
| 元にない文の生成 | AIの要約と元の投稿を並べて表示する。AIの出力に「AIによる提案」と表示する |
| 相違点・共通点 | 別のLLM呼び出しで生成し、仮説として表示する |
| 議論の問い | 同上。ファシリテーターが編集・選択する |
| 結果の編集 | 本アプリのDBに、AI結果とは別に保存する |

## Alternatives Considered

- **Polis**: 外部APIの有無と日本語対応が未確認である。構成が大きく、運用の負荷が高い
- **いどばた**: 分析基盤ではなく、意見収集まで含むWebアプリである。更新も古い
- **広聴AIの組み込み・フォーク**: AGPLの義務が及ぶ範囲が広がる。追従と保守の負荷も増える
- **独自実装（LLMで直接グルーピング）**: 品質を自分たちで担保する必要がある。広聴AIが合わなくなった場合の選択肢として残す

## Consequences

- アダプター越しなので、将来の差し替えができる
- AGPLのネットワーク利用条項が、別プロセス呼び出しに及ぶ範囲は未確認である。公開前に専門家へ確認する
- 広聴AIはPythonとDockerで動く。本アプリと別のホストが必要になり、常時起動の費用が課題になる
- 依存の固定が必要である。評価では、GitHubの固定コミットと `polars<2` が必要だった
- LLMの費用は、概算で1件あたり約1,000トークンである（40件の実測からの換算）。月間の利用上限を超えると、分析が失敗する
- 失敗の原因が分析基盤のログに出ないことがある。アダプターで、エラーの詳細を保存する必要がある

## 未決事項への提案

次の事項は、ユーザーの判断が必要である。ここでは選択肢と推奨のみを示す。

| 項目 | 推奨 | 理由 |
| --- | --- | --- |
| フロントエンド | Vite + React + TypeScript | dev-standardsの標準に合う |
| バックエンド・DB | 要判断。サーバレス（API + KVS）か、単一コンテナ + RDB | 分析ジョブと履歴の要件を満たす最小構成を、次のIssueで比較する |
| 分析基盤の置き場所 | イベント時だけ起動する方式を検討 | 常時起動の費用を避けられる。起動時間の許容は未確認 |
| ファシリテーター認証 | 管理用の使い捨てトークン付きURLから開始 | 最小で保護できる。後からアカウント認証へ移行できる |
| 匿名投稿の編集・削除 | 投稿時に発行するキーを、ブラウザ側にだけ保存する | 識別情報を保存せずに、本人の編集を許せる |
