# ADR-0002: 運営者の認証にイベントごとの失効できるトークンを使う

- Status: Accepted
- Date: 2026-10-25

## Context

#21 では、環境変数 `ADMIN_TOKEN` による共有の1つのトークンで、運営者を認証した。
この方式には、次の問題がある。

- 渡した相手を区別できない
- 1人に渡したトークンだけを無効にできない
- どのイベントでも操作できてしまう

運営者の作業は、スマホで、イベント当日に行う。
アカウント登録やパスワードの管理は、負担が大きい。

## Decision

2種類の権限を設ける。

| 権限 | 認証 | できること |
| --- | --- | --- |
| オーナー | 環境変数 `ADMIN_TOKEN` | すべて。イベントの作成と、運営者のリンクの発行・失効を含む |
| 運営者 | イベントごとの運営者トークン | 担当のイベントのセッション設定・投稿の閲覧・分析 |

運営者トークンの仕様は次のとおりとする。

- 256ビットの乱数で、`opm_` で始まる。推測はできない
- 保存するのはSHA-256のハッシュだけである。本体は、発行時の1回しか表示しない
- 名前（例: 会場係）を付け、一覧で区別できる
- 失効できる。失効は取り消せず、必要なら新しく発行する
- リンク `/admin#token=...` として渡す。`#` のあとはサーバーに送られず、アクセスログにも残らない。画面は読み込み後にアドレスから消す
- 運営者が担当外のイベントを指すと、403を返す。存在しないものを指したときも同じにし、存在の有無を教えない

イベントのIDやセッションのIDは、認証の代わりに使わない。
参加者のURLに含まれるセッションIDは、投稿のためのもので、運営の権限を与えない。

## Alternatives Considered

- **アカウント認証（Cognito等）**: 運営者の登録とパスワードの管理が要る。イベント時だけ使う用途に重い。必要になれば、同じ権限の仕組みの前段に足せる
- **使い捨てトークンURL（一度開くと無効）**: スマホで開き直したり、別の端末で開いたりできない。失効できる長期のトークンのほうが運用しやすい
- **イベントの共有パスコード**: 短くなり、推測できる。個別の失効もできない
- **共有の `ADMIN_TOKEN` のまま**: 上記の問題が残る

## Consequences

- リンクを知っている人は運営できる。渡す相手と経路に気をつける必要がある
- オーナーのトークンは、環境変数で管理する。変更はデプロイが要る
- 投稿の削除とエクスポート（#32 など）は、同じ仕組み（担当イベントの確認）に載せる
- 運営者の操作の記録（誰が何をしたか）は、まだない。必要になったら別に扱う
