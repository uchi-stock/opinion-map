# ADR-0003: 匿名性を保ったまま、投稿の頻度を抑え、投稿者と運営者が投稿を直せるようにする

- Status: Accepted
- Date: 2026-10-25

## Context

仕様書では、スパム対策・投稿頻度の制限と、匿名投稿の編集・削除が検討事項になっていた。
匿名性が最優先なので、投稿者を特定できる情報（IPアドレス、端末の識別子、アカウント）は保存しない。
一方で、会場では参加者が一斉に投稿するので、正当な集中を止めてはいけない。

## Decision

### 投稿頻度の制限

セッションごとに、一定時間の投稿数の上限を設ける。初期値は1分に120件である。

- 数えるのは、保存済みの投稿の作成時刻だけである。新しい個人の情報は何も保存しない
- 誰の投稿かは見ない。全体の量を抑えるので、1人の連投も、多数の投稿の集中も、同じ上限で抑える
- 同じ送信IDの再送は、数えない（通信が不安定でも、投稿が失われないようにする）
- 超えると429を返し、少し待つよう案内する
- 上限は設定で変えられる

### 投稿者による編集・削除

投稿時に、ブラウザが投稿ごとの乱数の鍵を作る。

- 鍵は、128ビット以上の乱数で、投稿ごとに別の値にする
- サーバーには、鍵のハッシュだけを保存する。鍵はこのブラウザにだけ残る
- 鍵が合う投稿だけ、編集と削除ができる。鍵の誤り、鍵のない投稿、存在しない投稿は、同じ403にする
- 編集は、受け付け中のセッションだけにする。削除は、いつでもできる
- 削除すると、本文を消し、過去の分析の入力の記録からも本文を消す
- 鍵は投稿ごとに別なので、同じ人の投稿どうしを結びつけない

### 運営者による非表示・削除

運営者（オーナーと、担当イベントの運営者）が、投稿を操作できる。

- 非表示は、元に戻せる。参加者の一覧と、以後の分析の入力から外れる。運営者の一覧には印付きで残る
- 削除は、元に戻せない。本文を消し、過去の分析の入力の記録からも消す

## Alternatives Considered

- **IPアドレスごとの制限**: 会場の共有回線では、多数の参加者が同じIPになり、正当な投稿を止める。IPの保存も避けたい
- **端末の識別子（ブラウザ指紋など）**: 人を追跡する情報であり、匿名性に反する
- **ハッシュ化したIPの短期保存**: 生のIPは残らないが、投稿者の手がかりになりうる。共有回線の問題も残る。今は採用せず、問題が出たときに再検討する
- **投稿を通して共通の鍵を使う**: 同じ人の投稿どうしが結びつく。匿名性を弱める
- **CAPTCHA**: 会場のスマホでの入力の負担が大きい。必要になれば追加する

## Consequences

- 1人が多数の投稿を連投することは、全体の上限に達するまで防げない。運営者が非表示にして対応する
- 鍵を保存したブラウザを失う（履歴の削除、別の端末）と、自分の投稿を直せなくなる。その場合は、運営者に依頼する
- プライベートブラウズでは、鍵が残らないことがある。投稿自体はできる
- 削除は、AIが作った要約など、派生した内容までは消さない。分析をやり直すと、削除した投稿は含まれない
- 投稿頻度の上限は、ストレージの実装（DynamoDB）では、作成時刻での範囲検索が要る
