# 本番へのデプロイ

本番の構成と、スマホのブラウザだけで行うデプロイの手順をまとめる。
構成管理は OSLS（Serverless Framework のオープンソース版）である。定義は `backend/serverless.yml` にある。

## 構成

1つのスタック（`opinion-map-prod`）に、次をまとめる。

| リソース | 役割 |
| --- | --- |
| DynamoDB | データの保存。1つのテーブルと、一覧用の GSI1 |
| Lambda と API Gateway | API。1つの関数が、内部でルーティングする |
| S3 | 画面（フロントエンド）の置き場。非公開 |
| CloudFront | 同じドメインで、画面と API を配信する |
| ECS（Fargate）と ECR | 広聴AIの分析。分析1回ごとに、タスクを1つ起動する |
| S3（分析用） | 分析の入力と結果の受け渡し。取り込んだら消え、消し忘れても2日で消える |

- 画面は `https://<ドメイン>/`、API は `https://<ドメイン>/api/*` で配信する。同じドメインなので、CORS の設定は要らない
- `/s/<ID>` や `/admin` など、拡張子のないパスは、CloudFront Function が `index.html` で返す。API の 404 は、そのまま返す
- S3 は、CloudFront からの読み取りだけを許可する
- DynamoDB のテーブルは、スタックを消しても残る。ポイントインタイムリカバリを有効にしている

## 必要な設定（GitHub の Settings → Secrets and variables → Actions）

AWS のキーは必須である。オーナーのログインは、Google ログインか合言葉の、どちらかを用意する。

| 種類 | 名前 | 用途 |
| --- | --- | --- |
| Secret | `AWS_ACCESS_KEY_ID` | デプロイに使う IAM ユーザーのキー |
| Secret | `AWS_SECRET_ACCESS_KEY` | 同上 |
| Secret または Variable | `GOOGLE_OAUTH_CLIENT_ID` | Google ログインのクライアントID |
| Secret（任意） | `SESSION_SECRET` | ログイン後のセッションの署名鍵。32文字以上のランダムな文字列。なければ、AWS のシークレットキーから自動で作る |
| Secret または Variable | `OWNER_EMAILS` | 最初の管理者にする Google アカウントのメールアドレス。カンマ区切り。管理者の一覧が空のときだけ使う初期値で、以降の追加・削除は管理画面で行う |
| Secret（任意） | `ADMIN_TOKEN` | 合言葉でのログイン。Google ログインを使うなら不要 |
| Secret（任意） | `GEMINI_API_KEY` | 共通点・相違点・問いの案に使う |
| Variable（任意） | `AWS_REGION` | 既定は `ap-northeast-1` |

- `SESSION_SECRET` を自動で作る場合、AWS のキーを入れ替えると値が変わる。発行済みのセッションは使えなくなり、ログインし直しになる
- 管理者の一覧に載っていないアカウントは、Google でログインできても、オーナーになれない
- 管理者の一覧は、アプリ側(DynamoDB)で持つ。管理者が、管理画面の「管理者」から追加・削除する
- 初回のログインで、`OWNER_EMAILS` の内容が一覧に登録される。登録後に `OWNER_EMAILS` を変えても、一覧は変わらない
- 一覧から外すと、発行済みのセッションも、次のリクエストから使えなくなる。最後の1人は外せない
- `ADMIN_TOKEN` は、AWS の Lambda の環境変数に平文で入る。AWS のコンソールを見られる人は、読める

## デプロイの手順（スマホで完結）

1. GitHub の Actions 画面で「CD」を開く
2. 「Run workflow」を押す(自動では、採番のあとに自動で走る)
3. 完了を待つ。初回は、CloudFront の作成に10分ほどかかる
4. 実行の Job Summary に、公開URLと、動作確認の結果が出る
5. **初回だけ**: Google Cloud Console の OAuth クライアントを開く。「承認済みの JavaScript 生成元」に、公開URL（`https://xxxx.cloudfront.net`）を追加する
6. 公開URLの `/admin` を開き、「Google でログイン」を押す

5 の追加をしないと、Google のボタンを押してもログインできない。公開URLは、1回目のデプロイが終わるまで分からない。

動作確認では、次を自動で確かめる。

- 画面（`/` と `/admin`）が返る
- `GET /api/health` が返る
- トークンなしの運営者 API が 401 を返す
- 存在しないセッションが 404 を返す（DynamoDB まで届いている）
- Google ログインが有効である（設定している場合）
- 合言葉で一覧を読める（設定している場合）

## IAM ユーザーに必要な権限

デプロイ用の IAM ユーザーには、次の権限が要る。

- CloudFormation（スタックの作成・更新）
- S3（Serverless のデプロイ用バケットと、画面のバケット）
- Lambda、API Gateway、DynamoDB、CloudFront
- IAM（Lambda の実行ロールの作成）
- CloudWatch Logs
- ECS、ECR（分析のタスクとイメージ）
- EC2の参照（`DescribeVpcs`・`DescribeSubnets`・`DescribeSecurityGroups`。分析のタスクを置くネットワークを調べる）

権限が足りないと、`osls deploy` が `AccessDenied` で失敗する。失敗した操作名がログに出るので、その権限を足す。

## 初回によくある失敗

- **オーナーのログインがない**: 最初の手順で止まり、足りない名前を出す。値は出さない
- **権限不足**: 上記のとおり、失敗した操作の権限を足す
- **初回の作成が失敗して、スタックが残った**: 状態が`ROLLBACK_COMPLETE`のスタックは、更新できない。ワークフローは、この状態を見つけると、消して作り直す。このとき、まだデータは無い
- **失敗のあとに、空の DynamoDB テーブルが残った**: テーブルは削除保護のため、スタックを消しても残ることがある。テーブル名は固定しないので、次の作成とはぶつからない。空のテーブルは、AWS のコンソールで消してよい
- **CloudFront を作れない**: アカウントの確認が済んでいないと、作成できないことがある。AWS のサポートの案内に従う

## 運用で知っておくこと

- 画面だけを更新したいときも、同じワークフローを使う。インフラに変更がなければ、`osls deploy` は短く終わる
- CloudFront のキャッシュは、デプロイごとに消す。`index.html` は、毎回確かめさせる設定である
- 参加者に配る招待URLは、イベントごとに1つ（`/e/<イベントID>`）。運営者が管理画面で、テーマを「開く」「閉じる」で切り替える。複数のテーマを同時に開ける。参加者が投稿できるのは、開いているテーマだけで、すべてのテーマを選んで見られる。これまでのテーマごとのURL（`/s/<ID>`）も使える
- 議題の提案（OST）を使うときは、管理画面のイベントのページで「議題の提案を受け付ける」をオンにする。参加者は招待URLの画面から議題を出し、いいねで関心を示す。運営者が承認すると、公開中のテーマができる。却下や統合をした提案は、参加者には見えない。提案者は記録されない
- テーマごとの議論の記録（結論、次の行動、未解決の問い）は、管理画面のセッションのページで書く。「参加者に公開する」にチェックを入れるまで、参加者には見えない。イベントのページで、全テーマの記録を1画面で見て、Markdownにしてコピーできる。担当者は名前の文字列だけで、個人が特定される情報は書かない。分析のあるセッションでは、「要約から下書きを取り込む」で、AIの要約から下書きを入れられる。取り込んだだけでは保存も公開もされず、確認して保存するまで、記録は変わらない
- 投稿は、「そのまま（原文）」と「要約（AI）」の2つの見方に分かれる。運営者は、分析のあとに、セッションのページで両方を切り替えて見られる。要約を参加者に見せるには、「この要約を参加者に公開する」にチェックを入れる。参加者に出るのは、概要とまとまりの要約と、運営者が採用した案だけで、AIによる要約と分かる注記がつく
- `feat`か`fix`をマージすると、新しいバージョンが採番されたあと、自動で本番にデプロイされる。`docs`や`chore`ではデプロイされない。手動の実行も、再実行やロールバック用に残してある(Actions の「CD」の「Run workflow」)
- バージョンは、mainへのマージごとに自動で採番される(`cd.yml`のsemantic-release)。`feat`は新機能(minor)、`fix`は修正(patch)で上がり、`docs`や`chore`では上がらない
- 採番されたバージョンは、デプロイで画面に反映される。トップページの「バージョン」で確認できる
- 広聴AIの分析は、次の「分析の仕組み」を参照する
- DynamoDB は、実機での動作を、このデプロイで初めて確かめる。動作確認が失敗したら、ログと CloudWatch Logs を確認する

## 障害の通知（運用監視）

障害に気づけるよう、CloudWatch の警報が、メールで知らせる。

| 警報 | 条件 |
| --- | --- |
| API のエラー | Lambda がエラーを返した（5分に1回でも） |
| API の 5xx | API が 5xx を5分に3回以上返した |
| 分析の失敗 | 広聴AIの分析が失敗した（ログの `analysis_failed`） |
| 画面のエラー | 画面の描画エラーが、15分に20件以上 |

### 設定（スマホで完結）

1. GitHub の Settings → Secrets and variables → Actions → Variables に、`ALERT_EMAIL` を登録する（通知を受け取るメールアドレス）
2. 「CD」の「Run workflow」で反映する
3. 届いた「AWS Notification - Subscription Confirmation」のメールで、リンクを開いて購読を確定する。確定するまで、通知は届かない
4. `ALERT_EMAIL` が未登録のときは、警報は作られるが、通知先は無い。CD の実行に警告が出る

### ログに残すもの

- ログは30日で消える
- 障害の検知に使う出来事（`analysis_failed`、`server_error`、`client_error`）だけを、1行のJSONで出す
- 投稿の本文、メールアドレス、トークンは出さない。分析の失敗はコードだけ、予期しないエラーは種類の名前だけを残す
- 画面のエラーは、メッセージ（200文字まで）とパスだけを送る。クエリとハッシュは送らない。量は、1日200件までに抑える

## 依存の更新と、セキュリティ検査

### CodeQL

コードの脆弱性とバグのパターンを、PR、mainへのマージ、毎週月曜に検査する（`codeql.yml`）。

- 結果は、GitHub の Security タブの「Code scanning」で見られる（スマホのブラウザで見られる）
- 指摘が出たら、内容を見て、直すか、理由を書いて却下する

### Renovate（依存の自動更新）

依存の更新のPRを、自動で作る（`renovate.json`）。

- minor と patch は、週に1回（月曜の朝）、1つのPRにまとめる。major は別のPRになる
- 公開から3日たったものだけを対象にする（公開直後の異常を避ける）
- **Renovate のPRは、自動ではマージしない**。PRのコメントに出る、更新の種類と直接・間接のリスクの要約を見て、人が判断してマージする
- 初回だけ、Renovate の GitHub アプリを、このリポジトリに入れる必要がある。https://github.com/apps/renovate を開き、「Configure」でこのリポジトリを選ぶ（スマホで完結する）
- 入れると、最初に「Configure Renovate」のPRが来ることがある。内容を見て、問題なければマージする
- 開発用の依存（semantic-release など）に、`npm audit` の警告が出ている。実行時には使わない。更新のPRで、少しずつ解消する

## 費用の歯止め（AIの利用）

分析と案の生成は、実行のたびに費用がかかる。誤操作や使いすぎを防ぐため、上限を3段で設ける。

### 1. アプリの1日の上限

イベントごと、日本時間の1日あたりで数える。上限に達すると、分析や案の生成は断られ、メッセージに戻る時刻が出る。

| 設定 | 意味 | 既定 |
| --- | --- | --- |
| `ANALYSIS_DAILY_LIMIT` | 分析を始められる回数 | 10 |
| `INSIGHT_DAILY_LIMIT` | 案を作れる回数 | 100 |

- GitHub の Settings → Secrets and variables → Actions → Variables に登録する。未登録なら既定を使う
- 0 にすると、AIを止められる（すべて断る）
- 変更したあとは、「CD」の「Run workflow」で反映する
- 今日の使用量は、管理画面のイベントのページ「AIの利用状況」で見られる

### 2. AWS の予算アラート

費用が想定を超えたときに、メールで気づくための設定である。スマホのブラウザで設定できる。

1. AWS のコンソールで「Billing and Cost Management」を開く
2. 「Budgets」→「Create budget」を選ぶ
3. 「Cost budget」で、期間を月次にして、金額を決める（実際の利用額の2倍程度から始める）
4. 通知の条件を「実際の費用が80%を超えたとき」にして、メールアドレスを入れる

### 3. Gemini の上限

- Google Cloud コンソールの「お支払い」→「予算とアラート」で、予算とメール通知を設定する
- 「APIとサービス」で Generative Language API の「割り当て」を開き、1日のリクエスト数の上限を下げる。こちらは、アプリの上限が破られた場合の最後の歯止めになる

## 分析の仕組み（広聴AI）

運営者の画面で「分析する」を押すと、分析1回ごとに、Fargate のタスクを1つ起動する。

1. アプリが、入力（投稿の本文）と設定を、分析用の S3 に置く
2. Fargate のタスクが起動し、広聴AIの CLI（`kouchou-analyze`）を実行する。広聴AIは改造せず、既定のプロンプトのまま動かす
3. タスクが、結果を S3 に置いて終わる。アプリは、結果を取り込み、S3 の入力と結果を消す

- タスクにはインターネットからの入口がない。通信は、S3・ECR・LLM（Gemini）への出口だけである
- 起動から結果まで、40件で3〜4分ほどを見込む（イメージの取得に1〜2分、分析に約2分）。分析がない間は、何も動いておらず、課金もない
- 失敗したときは、運営者の画面に理由が出る。理由に投稿の本文は含めない（LLMの利用上限、APIキー、メモリ、時間切れなどに分類する）
- イメージは、デプロイのたびに、`kouchou-runner/` から作り直して ECR に置く

### 動作を確かめる

Actions 画面の「分析基盤の動作確認」を実行する。サンプルの40件で、タスクを1回動かし、結果と未分類の算出までを確かめる。結果は Job Summary に出る。

### 制限事項

- 出口は、セキュリティグループで 443（HTTPS）に限れるが、LLM のドメインだけには絞れない。ドメインで絞るには、AWS Network Firewall などが要る（費用がかかる）。いまは見送っている
- タスクは、既定のネットワーク（VPC）の公開サブネットに置き、公開 IP を付ける（NAT なしで、イメージの取得と LLM の呼び出しをするため）。入口は、既定のセキュリティグループが、同じグループの中からだけに限る
- `GEMINI_API_KEY` は、タスクの定義に環境変数として入る。AWS のコンソールを見られる人は、読める
- 分析のタスクに送る投稿の本文は、LLM の提供元（Google）にも送られる。実データを流す前に、Gemini の規約と、プロジェクトの課金状態（入力が学習に使われないか）を確認する
